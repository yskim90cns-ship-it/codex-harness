# Architecture Decision Records

## 철학
실시간 음성 번역은 사용자가 지연 시간과 신뢰도를 바로 체감하는 제품이다. MVP는 화려한 기능보다 빠른 시작, 명확한 상태 표시, 안전한 API 경계, 테스트 가능한 세션 로직을 우선한다.

---

### ADR-001: Next.js App Router 선택
**결정**: Next.js App Router 기반으로 웹사이트와 서버 API 라우트를 함께 구현한다.

**이유**: 마이크 입력과 실시간 UI는 브라우저에서 처리하고, 외부 번역 API 호출은 서버 라우트에서 보호할 수 있다. 하나의 코드베이스 안에서 페이지, API, 타입, 테스트를 함께 관리하기 쉽다.

**트레이드오프**: 순수 백엔드 서버나 별도 WebSocket 서버보다 초기 실시간 스트리밍 제어는 제한적일 수 있다. MVP에서는 짧은 텍스트 단위의 실시간 번역으로 시작하고, 필요할 때 전용 스트리밍 서버를 추가한다.

### ADR-002: TypeScript strict mode 사용
**결정**: TypeScript strict mode를 사용하고, 음성 세션/번역 결과/오류 상태를 명시적 union type으로 정의한다.

**이유**: 실시간 기능은 `idle`, `listening`, `translating`, `error` 같은 상태 전이가 많다. 타입으로 상태를 제한하면 UI가 불가능한 조합을 렌더링하는 문제를 줄일 수 있다.

**트레이드오프**: 초기 타입 작성 비용이 늘어난다. 대신 세션 로직과 테스트의 안정성을 얻는다.

### ADR-003: 외부 API 호출은 서버 라우트로 격리
**결정**: 번역, 서버 전사, 모델 호출 등 외부 API 요청은 `app/api/*/route.ts`에서만 수행한다.

**이유**: API 키를 클라이언트에 노출하지 않고, 요청 검증/레이트 리밋/오류 매핑을 한 곳에서 관리하기 위해서다.

**트레이드오프**: 클라이언트가 외부 API에 직접 연결하는 방식보다 구현 단계가 하나 늘어난다. 보안과 운영 제어를 위해 이 비용을 감수한다.

### ADR-004: MVP는 브라우저 음성 인식 우선, 서버 전사는 확장 경로로 둔다
**결정**: MVP에서는 브라우저가 제공하는 음성 인식 기능을 우선 사용한다. 브라우저 지원이 부족하거나 품질이 부족한 경우를 위해 `app/api/transcribe`와 `services/transcriptionService.ts` 확장 지점을 문서화한다.

**이유**: 브라우저 음성 인식은 마이크 스트리밍 서버를 먼저 만들지 않고도 빠르게 실시간 전사 UX를 검증할 수 있다.

**트레이드오프**: 브라우저별 지원 범위와 인식 품질 차이가 있다. 제품 요구가 올라가면 서버 전사 방식으로 교체해야 한다.

### ADR-005: 전역 상태 라이브러리 미사용
**결정**: MVP에서는 Redux, Zustand 같은 전역 상태 라이브러리를 도입하지 않고 `useReducer`와 custom hook으로 세션 상태를 관리한다.

**이유**: 상태 범위가 번역 화면 하나에 집중되어 있고, 외부 저장소 없이도 테스트 가능한 reducer로 충분히 표현할 수 있다.

**트레이드오프**: 여러 페이지에서 세션을 공유하는 기능이 생기면 구조를 다시 검토해야 한다.

### ADR-006: 세션 데이터는 기본적으로 저장하지 않음
**결정**: 원문 전사와 번역 히스토리는 MVP에서 브라우저 메모리에만 유지하고 서버에 저장하지 않는다.

**이유**: 음성 및 대화 내용은 민감할 수 있다. 저장 기능 없이 시작하면 개인정보 위험과 운영 복잡도를 줄일 수 있다.

**트레이드오프**: 사용자가 새로고침하면 히스토리가 사라진다. 저장/내보내기 기능은 명시적인 사용자 액션이 있을 때 별도 기능으로 추가한다.
